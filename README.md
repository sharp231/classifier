# End-to-End Image Classification App (CIFAR-10)

画像認識モデルの学習から Web アプリケーションとしてのデプロイまでを、End-to-End で実装したプロジェクトです。  
ユーザーがアップロードした画像を AI が解析し、CIFAR-10 の 10 クラスに分類します。

## プロジェクト概要

機械学習モデルを作成するだけでなく、実際の Web サービスとして動作させるための設計、実装、デプロイまでを行いました。
入力画像の向きや縦横比の違いを吸収する前処理、画像の向きや縦横比を整える前処理を、本番とテストで共有しています。
Webアプリでは、CIFAR-10の比較評価に基づき、前処理した画像を
学習済みモデルに1回渡す単一推論（Baseline）を採用しています。
TTAは比較評価で使用し、主要な処理は pytest と GitHub Actions で検証しています。
pytest と GitHub Actions による自動テストを取り入れています

- **担当領域:** 企画・要件定義 / モデル構築 / Web 実装 / テスト / デプロイ

## 設計の意図（課題 → 解決策 → 成果）

### 1. 前処理と推論の責務分離

**課題**  
Web アプリと単体テストが別々の前処理を使っていたため、テストが通っても、Web アプリ側の変更を検証できない場合がありました。

**解決策**
- `preprocessing.py` に、EXIF 回転補正、RGB 変換、クロップ、32×32 への調整、正規化を集約しました。
- `inference.py` にモデルの呼び出しとクラスごとの予測値の平均処理を分離し、Web アプリと評価スクリプトで共有しました。
- `app.py` は、アップロードの受付から結果画面の返却までを担当し、共通推論が返す10クラスの予測値から上位3件を表示します。

**成果**  
単体テストで Web アプリと同じ前処理を検証できるようになりました。比較評価でも Web アプリと同じ推論処理を使えるため、クロップ比率を変えた場合の影響を比較できます。

### 2. アップロード画像の検証とエラー処理

**課題**  
ファイルの拡張子だけでは、中身が有効な PNG・JPEG かどうかや、処理できるサイズかどうかを判断できません。

**解決策**
- 保存前に、拡張子、申告された MIME タイプ、Pillow が判定した画像形式が一致することを確認します。
- ファイルサイズ、画像の縦横サイズ、総ピクセル数を制限し、画像をデコードできることを確認します。
- 検証エラーは `UploadValidationError` で扱い、内容に応じたメッセージと HTTP ステータスを返します。
- 検証済みの画像は UUID を使ったファイル名で保存し、保存や推論が失敗した場合は対象ファイルを削除します。

**成果**  
形式の不一致、破損、サイズ超過を保存前に検出できるようになりました。利用者は画面で失敗理由を確認でき、運用時はログから処理の経過を追えます。

### 3. 比較評価に基づく推論方式の選択

**課題**  
画像を加工して複数回推論する TTA は処理時間が増えます。今回のモデルで正解率が改善するかは、実測が必要でした。

**解決策**  
`evaluate_model.py` を使い、同じ学習済みモデルと CIFAR-10 テストセット10,000件で比較しました。単一推論（Baseline）は比率 `1.0` で1回推論し、TTA は比率 `1.0`、`0.8`、`0.65` で推論した結果をクラスごとに平均します。

| 推論方式 | Top-1 正解率 | 1画像あたりの処理時間 |
| --- | ---: | ---: |
| Baseline | 65.20% | 70.95 ms |
| TTA | 58.71% | 175.08 ms |

**成果**  
今回の比較では、Baseline の正解率が6.49パーセントポイント高く、処理時間も短かったため、Web アプリの既定方式に採用しました。クラス別の結果と測定条件は [評価レポート](evaluation_10000.json) で確認できます。

処理時間はローカル環境での前処理と推論を含みます。評価に用いたデータは学習時の検証にも使用しています。

**運用上の工夫**

- モデルは最初の画像判定が必要になった時点で読み込み、アプリ起動時の負荷を抑えています。
- Python 標準の `logging` で、アップロード、モデルの読み込み、推論完了、エラーを記録します。推論完了ログでは、使用したクロップ比率と推論回数を確認できます。

## Testing / CI

GitHub Actions で、PR 作成・更新時と `main` への push 時に `pytest` を実行します。

- Web フロー、画像アップロードの検証、失敗時のファイル削除
- 共通前処理（RGB 変換、正規化、クロップ、EXIF 回転補正）
- 単一推論（Baseline）と TTA の平均計算

推論テストにはテスト用モデルを使います。実モデルの比較評価は `evaluate_model.py` で行います。

```bash
uv run pytest
```

## Renderへのデプロイ

Render Web Serviceでは、以下の設定を使用します。

| 項目                 | 設定値                                                      |
| :------------------- | :---------------------------------------------------------- |
| Runtime              | Python 3                                                    |
| Build Command        | `uv sync --frozen --no-dev`                                 |
| Start Command        | `uv run gunicorn app:app --bind 0.0.0.0:$PORT --log-file -` |
| Environment Variable | `PYTHON_VERSION=3.13.5`                                     |

`uv.lock` をリポジトリ直下へ配置することで、でも固定された依存関係を使用します。

### アップロード画像の保存

アップロード画像は `data/uploads` に一時保存されます。
Render Freeのローカルファイルシステムは永続化されないため、再デプロイ、再起動、スピンダウン時に画像は削除されます。現在の画像判定用途では一時保存として扱い、永続的なデータ収集には使用しません。
将来、誤分類画像の収集やMLOpsへ利用する場合は、外部オブジェクトストレージの導入を検討します。

ブラウザで `http://127.0.0.1:5000` にアクセスしてください。
